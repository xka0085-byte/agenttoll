# x402 交付回执与托管扩展规范（草案）— 中文对照版

> 英文版已推送：https://github.com/xka0085-byte/agenttoll/blob/master/docs/specs/x402-receipts-draft.md

## 1. 摘要

本草案提议向 x402 协议添加一个**可选扩展**：为 agent 交易加入**带链上托管与验证的交付回执**。x402 解决了支付的声明与结算；它刻意不保证卖家交付承诺的东西。本扩展填补这个缺口：付款先入托管，交付对照内容指纹进行验证，每笔完成的交易产生一张**永久、防篡改的链上回执**。

## 2. 动机

x402 是先付钱模式：agent 先付款再重试请求。这造成不对等——买方承担全部交付风险。今天的后果：

1. **价值天花板。** 买方只敢向已信任的卖家冒大额风险。陌生对手方之间的高价值交易无法发生。
2. **没有纠纷解决。** agent 以机器速度和体量成交；人类不可能仲裁。没有中立的记录留存「当初约定了什么」和「实际交付了什么」。
3. **没有信誉底座。** 生态中正在涌现的信用/信誉系统需要一层「已验证交易」的原始数据。目前没有任何标准化方案提供。

本扩展是**可选且增量**的：不需要它的交易完全照旧。

## 3. 术语

| 术语 | 含义 |
|---|---|
| **Escrow（托管）** | 中立持有账户。资金锁定直到验证通过或退款。 |
| **Contract digest（合同指纹）** | 对规范化交易条款（买什么、价格、交付规格）的 `SHA-256`。付款前锁定。 |
| **Deliverable digest（交付物指纹）** | 对交付内容的 `SHA-256`，由卖家在交付时提交上链。 |
| **Verifier（验证器）** | 链上程序，比对指纹，放款或退款。 |
| **Receipt（回执）** | 完成交易的永久链上记录。 |
| **DigestConflict（指纹冲突）** | 任一指纹检查失败时抛出的错误——条款被改或交付不符的信号。 |

## 4. 交易生命周期

```
INTENT 意图     买卖双方就条款达成一致；合同指纹上链锁定
ESCROW 托管     买方付款进入托管（不是直接给卖家）
DELIVER 交付    卖家线下交付内容；将交付物指纹提交上链
VERIFY 验证     验证器执行 C1–C5 五项检查
SETTLE 结算     全部通过 → 放款给卖家；铸回执
                任一失败 → 自动退款；记录失败
```

## 5. 验证检查（C1–C5）

| 检查 | 回答的问题 |
|---|---|
| C1 合同匹配 | 现行协议与锁定的合同指纹一致吗？ |
| C2 交付物匹配 | 交付内容与承诺的交付物指纹一致吗？ |
| C3 篡改检测 | 托管后条款被改过吗？（违反即抛 `DigestConflict`） |
| C4 时限 | 交付发生在约定期限内吗？ |
| C5 金额 | 结算金额与约定价格一致吗？ |

注意范围：指纹验证证明的是**一致性与完整性**——交付的字节就是双方约定的内容。它不判断主观质量；质量保障属于应用层，回执如实记录这一点。这让验证器保持极简、便宜、不越权。

## 6. 回执格式（v0）

```json
{
  "receipt_version": 1,
  "x402_payment_ref": "<x402 结算引用>",
  "buyer": "<钱包地址>",
  "seller": "<钱包地址>",
  "contract_digest": "<sha256-十六进制>",
  "deliverable_digest": "<sha256-十六进制>",
  "checks": { "C1": true, "C2": true, "C3": true, "C4": true, "C5": true },
  "outcome": "settled(已结算) | refunded(已退款) | expired(已过期)",
  "amount": { "value": "0.001", "asset": "USDC", "chain": "solana" },
  "timestamp": "<unix 时间戳>",
  "uri": "<指向完整条款的可选指针>"
}
```

回执按内容寻址、不可变。它们被设计为生态信誉/信用系统的**原始数据层**——任何评分方都可以基于回执构建，无需信任任何单一清算商。

## 7. 与 x402 的关系

- **不改动核心协议。** 402 流程原封不动。
- 扩展挂在结算层，类似现有清算商的扩展点：买方 agent 在支付意图中声明支持托管；接受的卖家通过托管验证器结算，替代直接结算。
- 卖家接收托管付款**零集成成本**——结算到账就是一笔普通转账，外加一张回执。

## 8. 安全考量

- 托管账户必须由程序控制（没有任何人工私钥能提款）。
- 指纹的抗碰撞性防止伪造交付物去匹配锁定的指纹；条款的规范化序列化必须明确指定，避免序列化歧义（见开放问题 Q1）。
- 退款路径必须有时间上限，防止托管锁死式攻击。

## 9. 参考实现

AgentToll 在 **Solana** 上实现了本草案：用程序衍生账户（PDA）做托管，用链上验证器执行 C1–C5。已上线并通过测试，作为 Colosseum Crypto World's Fair 参赛项目：仓库 `xka0085-byte/agenttoll`。

## 10. 开放问题

- **Q1：** 合同条款用于指纹计算的规范化序列化方式（JSON 规范形？CBOR？）
- **Q2：** 部分交付（多商品订单）是否应铸造部分回执？
- **Q3：** 回执隐私——敏感内容的指纹是否应加盐？
- **Q4：** 跨链回执：每链一张，还是桥接注册表？
